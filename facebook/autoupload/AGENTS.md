# Формат HTTP-екшенів та історії запитів

- Правила стосуються HTTP-автозаливів без браузера. Не змінювати контракт браузерних `api-actions` заради звітності.
- Публічний HTTP-екшен обгортати через `tracedAction(name, execute, metadata)` із `services/reports/HttpExchangeTrace.js`. Зберігати наявні поля результату та додавати `actionId`, `exchanges[]`; у workflow також повертається `httpHistory`.
- `exchanges[]` містить фактичні запити й відповіді, час, тривалість, HTTP-статус, мережевий код і належність до екшену. Історія потрібна для успіху, відмови, часткового виконання й переривання. Виняток містить `actionId` і `exchanges`.
- Внутрішні читачі, які повертають рядок, runtime, токени або клієнт (`getBio`, `getAboutSectionTokens`, `prepareNameContext`, `prepareSocialContext`), зберігають свій внутрішній контракт. Їхні мережеві звернення записуються в історію викликача. Не додавати службову історію в runtime або сесію.
- Не збирати історію вручну в кожному екшені: `FacebookWebClient` і `ProxyHttpClient` фіксують відповіді до парсингу, включно з перенаправленнями та кожною фактичною повторною спробою.
- Workflow / сервіс користувацької операції обгортати через `withHttpWorkflow`. Вкладені workflow використовують спільний журнал, паралельні екшени мають окремі контексти. Метадані повинні містити лише безпечні ID профілю та кроку.
- `httpHistoryPolicy.js` централізовано готує дані для звітів. Зберігати API/GraphQL-відповіді без обрізання вкладеності, масивів або довгих рядків, приховуючи credentials. Не передавати історію через загальний `AppLogger.sanitize`, який обрізає дані.
- Для сторінок отримання сесії, access token та runtime явно передавати `historyPurpose: "session"`, `"access-token"` або `"runtime"`. Їхній HTML не записувати повністю: зберігати статус, розмір, назви знайдених/відсутніх полів, ознаки credentials, login/checkpoint/consent і результат перевірки формату. Значення токенів не зберігати. Статичний JS позначати `historyPurpose: "static-resource"`; JS-ресурси й байти файлів замінювати описом.
- Для API зберігати структуроване `body` і початковий текст `rawBody` після приховування секретів, включно з невалідним JSON та HTML-відмовами. JavaScript Content-Type не є причиною приховувати API-відповідь. Результати окремих постів і About зберігати також у `action.finished`.
- JSONL-журнал записує `request.started` до HTTP-виклику, `request.finished` до парсера та результат екшену. Незавершений запит не означає, що Facebook нічого не змінив.
- У `AutouploadStore`, задачах та IPC зберігати компактні підсумки й `httpHistory`, без копій `exchanges`. Повну історію приєднувати до наявних звітів задач та оформлення акаунтів. Не створювати окремий тип звіту для кожного екшену.
- Збій запису журналу повертати як `httpHistory.storageWarning`; він не змінює підтверджений Facebook результат і не дозволяє повтор mutation.
- Зміни перевіряти mock-тестами без реальних запитів: успіх, GraphQL-відмова, невалідна відповідь, timeout, скасування, перенаправлення, повтори GET, приховування секретів та збереження/експорт повної історії.
