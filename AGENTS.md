# Інструкції для роботи з проєктом AdsBot

## Опис проєкту

Це Node.js-проєкт для бота, який керує AdsPower через API.
Проєкт використовує JavaScript та ECMAScript-модулі.

## Основні правила

- Усі коментарі в коді писати українською мовою.
- Усі запити до AdsPower виконувати тільки через клас `AdsPower`.
- Не надсилати запити до AdsPower API безпосередньо з `index.js`, сервісів або інших частин проєкту.
- Логіку взаємодії з AdsPower API зберігати централізованою у класі `AdsPower`.
- Усі запити до Keitaro виконувати тільки через клас `Keitaro`.
- Не надсилати запити до Keitaro Admin API безпосередньо з `index.js`, сервісів GUI або інших частин проєкту.
- Логіку взаємодії з Keitaro API зберігати централізованою у класі `Keitaro`.
- Перед внесенням змін перевіряти наявну реалізацію та використовувати вже створені методи й сервіси.
- Не дублювати код, якщо потрібна логіка вже існує в проєкті.
- Не змінювати файли в папці `node_modules`.
- Не розкривати й не додавати до репозиторію секретні дані з `.env`, дані проксі або дані профілів.

## Організація тестів

- `npm test` і `npm run test:campaign` запускають коротку безпечну перевірку створення рекламної кампанії.
- `npm run test:all` запускає повний набір локальних mock-тестів і використовується після наскрізних змін або перед релізом.
- Ручні сценарії з реальними AdsPower, Facebook або Grok знаходяться в `scripts/manual`.
- Не запускати файли з `scripts/manual` без прямої вказівки користувача.
- `npm run test:campaign:live` виконує лише явно дозволений Meta `validate_only` і не входить до автоматичних перевірок.

## Робота з класом AdsPower

- Публічні методи класу `AdsPower` мають використовувати внутрішній механізм виконання API-запитів.
- Черга запитів, затримки, обробка помилок і обмеження частоти запитів мають залишатися централізованими в класі `AdsPower`.
- Помилка одного запиту не повинна назавжди блокувати виконання наступних запитів.

## Перевірка змін

- Після змін запускати найменшу доречну перевірку.
- Після змін у запуску РК використовувати `npm run test:campaign`.
- Не запускати `npm run test:all`, якщо змінена ділянка повністю покривається коротким campaign-набором або одним цільовим тестом.
- Не виконувати небезпечні операції з реальними профілями AdsPower без прямої вказівки користувача.
- Після зміни публічного контракту Facebook API, Keitaro API або proxy client оновлювати відповідний документ у папці `docs`.

## Спілкування з користувачем

- Завжди спілкуйся українською мовою.
- Пояснюй усе простою, зрозумілою мовою (як для новачка, який тільки починає).
- Уникай складного жаргону або одразу пояснюй терміни простими словами.
- Розбивай усе на маленькі кроки і пояснюй послідовно.
- Будь терплячим і перевір розуміння перед тим, як йти далі.

## Навігація по структурі проєкту

Нижче наведено короткий індекс: за ним можна швидко визначити, де шукати потрібну логіку.

```text
AdsBot/
├── classes/       інтеграції із зовнішніми системами
├── facebook/      модулі автоматизації Facebook у браузері та Graph API
├── services/      перевикористовувані сервіси та бізнес-логіка
├── workflows/     послідовні операції над одним профілем або акаунтом
├── scenarios/     сценарії, що поєднують кілька workflow
├── frontend/      Electron + React GUI
├── scripts/       запуск тестів і ручні сценарії
├── test/          локальні mock-тести backend-частини
├── data/          локальні конфіги, шаблони, логи та результати роботи
├── docs/          документація API, GUI та ключових підсистем
├── artifacts/     локальні артефакти браузерних профілів; не є кодом
├── index.js       точка запуску основного Node.js-сценарію
├── config.js      загальна конфігурація застосунку
├── package.json   npm-команди та залежності кореневого проєкту
└── README.md      короткий опис, налаштування та базові команди
```

### Кореневі файли

- `index.js` — поточна точка запуску backend-сценарію. Тут не повинно бути прямих запитів до AdsPower або Keitaro.
- `config.js` — завантаження та підготовка конфігурації.
- `package.json` — команди `start`, `test:campaign`, `test:all`, команди GUI та залежності.
- `README.md` — короткий вступ у проєкт і базове налаштування.
- `.env` — локальні секрети й змінні середовища; не читати, не копіювати та не додавати до Git.
- `AGENTS.md` — правила роботи для агентів. Додаткові правила можуть бути в `classes/AGENTS.md`, `facebook/actions/AGENTS.md` і `facebook/modals/AGENTS.md`.

### Backend та інтеграції

- `classes/AdsPower.js` — єдина точка роботи з AdsPower Local API. Тут централізовані черга, затримки, обмеження частоти й обробка помилок.
- `classes/Keitaro.js` — єдина точка роботи з Keitaro Admin API.
- `facebook/api/` — клієнти та методи Facebook Graph API (`FacebookGraphApi.js`, створення API-клієнтів).
- `facebook/services/` — backend-сервіси Facebook, які об'єднують API та доменну логіку.
- `services/` — спільна бізнес-логіка:
  - `services/accounts/` — імена профілів, фото-набори та допоміжна логіка акаунтів;
  - `services/adspower/` — робота з групами AdsPower через клас `AdsPower`;
  - `services/campaigns/` — журнали створення рекламних кампаній;
  - `services/creatives/` — підготовка та керування креативами;
  - `services/gui/` — backend-стан, кеші та сервіси для GUI;
  - `services/images/` — завантаження зображень і читання їхніх розмірів;
  - `services/keitaro/` — логіка GUI та шаблонів потоків Keitaro;
  - `services/llm/grok/` — клієнт Grok і системні промпти;
  - `services/logging/` — журналювання застосунку та runtime-логер;
  - `services/pageRebuild/` — підготовка відновлення сторінок і датованого розкладу;
  - `services/personas/`, `services/profiles/` — персони та дані профілів комент-акаунтів;
  - `services/profile/` — перевірка стану профілю, стать і службові теги;
  - `services/proxy/` — нормалізація, перевірка, оновлення IP і HTTP-клієнт проксі;
  - `services/reports/` — збереження звітів задач;
  - `services/tasks/` — фонові задачі та їхні журнали;
  - `services/templates/` — шаблони кампаній і довідник країн;
  - `services/workflows/` — журнали довгих операцій, наприклад запуску креативів.

### Facebook-автоматизація

- `facebook/actions/` — окремі дії в інтерфейсі Facebook: клік, публікація, коментар, зміна профілю тощо.
- `facebook/browser/` — базові операції браузера: кліки, прокрутка, вказівник і таймінги.
- `facebook/selectors/` — CSS/XPath-селектори елементів Facebook. Якщо змінився інтерфейс Facebook, спочатку перевіряти цю папку.
- `facebook/state/` — визначення стану сторінки, авторизації, бану та автоматизованої поведінки.
- `facebook/state/checks/` — окремі перевірки стану.
- `facebook/modals/` — робота з модальними вікнами Facebook.
- `facebook/post/` і `facebook/post/checks/` — робота з постами та перевірки їхньої доступності.
- `facebook/accounts/` — керування Facebook-акаунтами.
- `facebook/workflows/` — завершені операції над Facebook-сторінками та постами, складені з окремих дій.

### Workflow та сценарії

- `workflows/profile/` — підготовка AdsPower-профілю та перевірка активності Facebook-акаунта.
- `workflows/accounts/` — налаштування комент-акаунта у профілі.
- `workflows/comments/` — виконання коментування через профіль.
- `scenarios/` — запуск комплексних операцій, зокрема послідовного або паралельного налаштування акаунтів і коментування.

### Desktop GUI

- `frontend/electron/` — Electron main process, preload, IPC-обробники та шляхи до файлів.
- `frontend/src/App.jsx` — кореневий React-компонент.
- `frontend/src/components/` — повторно використовувані компоненти інтерфейсу.
- `frontend/src/tabs/` — вкладки GUI: акаунти, сторінки, публікації, кампанії, Keitaro тощо.
- `frontend/src/lib/` — frontend API-клієнти та допоміжні функції.
- `frontend/src/styles/` — стилі GUI.
- `frontend/src/test/` — frontend-тести Vitest.
- `frontend/package.json` — залежності й команди frontend-частини.
- `frontend/dist/` — зібрана GUI-версія; генерується під час build і не редагується вручну.

### Тести, документація та локальні дані

- `test/` — backend mock-тести; вони не повинні працювати з реальними AdsPower, Facebook або Grok.
- `scripts/runTests.js` — маршрутизація короткого campaign-набору та повного mock-набору.
- `scripts/manual/` — ручні сценарії з реальними сервісами або профілями. Не запускати без прямої вказівки користувача.
- `docs/` — розширена документація: `facebook-api.md`, `keitaro-api.md`, `proxy-client.md`, `grok-client.md`, `creative-manager.md`, `gui.md`, `logging.md` та інші.
- `data/` — локальний runtime-стан і вхідні дані:
  - `data/facebookApi/` — конфіги акаунтів і проксі Facebook API; реальні файли містять секрети;
  - `data/creatives/` — оригінальні та підготовлені креативи;
  - `data/comments/` — тексти коментарів за країнами;
  - `data/generated-profiles-data/` — довідники для генерації даних профілів;
  - `data/prompts/` — промпти, зокрема для Grok;
  - `data/reports/` — звіти виконаних задач;
  - `data/logs/` — runtime-логи;
  - JSON-файли в корені `data/` — локальний стан GUI, шаблони, черги та журнали задач.
- `artifacts/` — збережені браузерні профілі та технічні файли запусків. Не використовувати як джерело програмної логіки й не додавати до комітів.
- `node_modules/` і `frontend/node_modules/` — встановлені залежності; не змінювати вручну.

### Як шукати зміни

- Потрібен новий запит AdsPower — перевірити або розширити `classes/AdsPower.js`.
- Потрібен новий запит Keitaro — перевірити або розширити `classes/Keitaro.js`.
- Потрібна нова дія у Facebook — додати її до `facebook/actions/`, а складну послідовність зібрати у `facebook/workflows/`.
- Потрібна операція над профілем — шукати у `workflows/profile/` та `services/profile/`.
- Потрібна зміна інтерфейсу — шукати відповідний компонент у `frontend/src/components/` або вкладку у `frontend/src/tabs/`.
- Потрібно змінити формат API або proxy client — оновити реалізацію і відповідний документ у `docs/`.
