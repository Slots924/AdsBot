# Перевірки профілю під час запуску

Спільні перевірки розділено на два етапи. Відкриття Facebook, керування браузером,
обробка доменних помилок і завершення сесії залишаються у відповідному workflow.
Обидві функції вимагають явно задати всі перемикачі свого етапу.

## Перед відкриттям профілю

```js
const readiness = await checkProfileBeforeLaunch({
    adsPower,
    profile,
    checks: {
        adsPowerReady: true,
        blockedTags: ["BAN", "LOGIN_ERROR"],
    },
});
```

Спочатку перевіряються заборонені теги, потім готовність AdsPower: проксі та чи
вільний профіль. Підтримувані теги: `BAN`, `LOGIN_ERROR`, `CHANGE_NAME_ERROR`.
Порожній список дозволяє всі теги. `adsPowerReady: false` вимикає перевірку
готовності, але залишає перевірку заданих тегів.

Результат: `{ ok, blockedTag, adsPowerReady }`. Значення `null` означає, що
перевірка не виконувалася. Невідомий тег або відсутній перемикач є помилкою.

Старі прямі виклики `ensureAdsPowerProfileReady(adsPower, profile)` та
`checkProfileHealth(adsPower, profile)` зберігають блокування BAN і Login Error.
Спільний етап передає їм порожній список, оскільки вже перевірив теги сам.

## На відкритій сторінці Facebook

```js
const facebook = await checkFacebookAfterLaunch({
    adsPower,
    profile,
    page,
    signal,
    checks: {
        loggedIn: true,
        active: true,
        ensureEnglish: false,
    },
});
```

Порядок: вхід, активність, англійська мова. Вимкнені перевірки не викликаються.
Невдалий вхід або неактивність зупиняють наступні перевірки. Перевірка активності
зберігає наявне відновлення locked-акаунтів і маркування тегами.

Результат: `{ ok, failedCheck, login, active, english }`, де результати перевірок
мають значення `true`, `false` або `null`. `failedCheck` містить назву перемикача
невдалої обов'язкової перевірки або `null`.

За замовчуванням `englishFailure: "stop"`: невдала зміна мови зупиняє перевірки.
`englishFailure: "continue"` зберігає необов'язкову зміну мови: `english` буде
`false`, але `ok` залишиться `true`. Винятки не приховуються в обох режимах.

`onCheck(check)` повідомляє про початок перевірки, `onResult(field, passed)` —
про її результат. Їх використовують для поточного етапу та часткового звіту.
`signal` перевіряється між діями й передається перевірці активності.
Параметр `actions` дозволяє підставити наявні дії workflow та mock-реалізації.

## Поточні налаштування

| Сценарій | Заборонені теги перед запуском | English | Невдала зміна мови |
| --- | --- | --- | --- |
| Персональні акаунти та БМ | BAN, LOGIN_ERROR | Вимкнено | — |
| Перевірка комент-акаунтів | BAN, LOGIN_ERROR | Увімкнено | Зупинка |
| Коментування | BAN, LOGIN_ERROR | Увімкнено | Продовження |
| Реакції на коментарі | BAN, LOGIN_ERROR | Увімкнено | Зупинка |
| UI-налаштування комент-акаунта | BAN, LOGIN_ERROR, CHANGE_NAME_ERROR | Залежить від skipEnsureEnglish | Продовження |
| API-налаштування комент-акаунта | Як у UI-налаштуванні | Вимкнено | — |
| Синхронізація Facebook API-клієнта | BAN, LOGIN_ERROR | Вимкнено | — |

Налаштування комент-акаунтів зберігає початковий відбір через
`getCommentAccountSetupSkipReason`, включно з тегами статі. При
`ignoreSkipReasons: true` тег CHANGE_NAME_ERROR дозволений, як і раніше.
Оновлення та перепідключення персональних і БМ-сесій перевіряють Facebook
без зміни мови й без перевірки, чи вільний уже відкритий профіль.

Ручні скрипти залишаються на попередніх викликах.
