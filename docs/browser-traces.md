# Діагностика браузерного оформлення акаунтів

Журнал автоматично працює у `executeCommentAccountSetupWithProfile`: ім’я, аватар,
обкладинка, очищення постів, публікація з датами та About. API-workflow не змінений.
Один екземпляр `BrowserTrace` обслуговує одне виконання над одним профілем.
Зовнішні API та LLM для журналу не викликаються.

## Де шукати збій

Результат workflow містить `browserTracePath`; той самий шлях додається до звіту
оформлення акаунтів. Він веде до:

```text
data/browser-traces/<run-id>/
  summary.md
  events.jsonl
  snapshots/<hash>.json
  failures/001/
    details.json
    fragment.html
    screenshot.png
```

Порядок читання для людини та LLM:

1. `summary.md`: невдалі кроки, посилання на збої та унікальні варіанти діалогів.
2. Потрібний `details.json`: етап, код помилки, локатор, хеш знімка.
3. Вказаний `snapshots/<hash>.json`: елементи, секції, стан кнопок, збіги локатора,
   видимість, перекриття й діагностичні властивості кандидатів.
4. `events.jsonl`, якщо потрібна попередня послідовність. `click.dispatched`
   означає відправлений клік; `click-confirmed` — появу очікуваного стану.

`fragment.html` — безпечне HTML-представлення вибраних елементів, **не оригінальний
DOM**. Воно не відтворює React і не дозволяє перевірити будь-який довільний CSS-селектор.
Виправлений селектор потрібно перевірити окремо на актуальній сторінці.
Screenshot створюється при збої після маскування особистих даних; може бути відсутній,
якщо сторінка закрилася, маскування не виконалося або вичерпано ліміт.

## Межі та приватність

- Значення полів, cookie, URL, HTML-скрипти, тексти стрічки й результати actions
  цілком не записуються.
- Поза формами залишаються лише відомі тексти інтерфейсу зі словників усіх дев’яти мов
  та наявних aria-label селекторів. Інші тексти позначаються `[приховано]`.
  Усередині діалогів і секцій відкритого About зберігаються короткі підписи та заголовки, включно з
  новими вікнами: з них прибираються відомі дані персони, назва профілю, поточні
  значення полів, email, номери, URL та довгі токени. Це дозволяє досліджувати нові модалки.
- Додаткові **перевірені написи інтерфейсу**, без імен та інших даних акаунта,
  можна передати у `traceUiTexts`. Це дозволяє поступово доповнювати словник доказів.
  Цей список не змінює селектори та не навчає програму натискати нові кнопки.
- На screenshot маскуються невідомі тексти, поля, фото, SVG, canvas, відео,
  iframe та фонові картинки. Жива сторінка отримує тимчасові маски; їх прибирання
  виконується у `finally`.
- Матеріали локальні та виключені з Git. Один запуск обмежений 160 знімками,
  2500 подіями, 30 збоями та приблизно 20 МіБ доказів; підсумок пишеться окремо.
- Однакові очищені знімки мають один файл. Повтор того самого збою на тому самому
  стані посилається на перший запис. Варіанти діалогів згруповані в підсумку.
- Ліміти діють на один запуск. Автоматичного видалення старих запусків немає.
  Папки завершених запусків можна видаляти як звичайні локальні журнали.

У workflow доступні `traceEnabled` (типово `true`), `traceDirectory` і `traceUiTexts`.
У класі додатково налаштовуються числові ліміти. Помилки запису не змінюють результат
action; їх кількість зазначена в підсумку, якщо його вдалося записати.

## Як підключити наступну дію

`trace.step(page, { id, goal }, action)` охоплює велику операцію. Прив’язка через
WeakMap діє тільки під час цієї операції; різні сторінки не змішують журнали.
Спільні pointer та confirmed-click автоматично додають спостереження та події.
`onProgress` зберігає межі внутрішніх операцій, включно з окремими постами й полями About.

Для внутрішнього збою, після якого action продовжить роботу або закриє форму:

```js
const trace = getBrowserTrace(page);
await trace?.failure(page, { point: "about.education", error });
```

Це потрібно робити **до** очищення форми, переходу, повторної спроби або закриття
профілю. Для звичайного переходу є `observe(page, { point, selector })`;
для технічного факту — `event(type, { point, expected, selector, status })`.
Довільні дані профілю або logger цілком передавати не потрібно.

## Рішення за станом сторінки

Workflow зберігає порядок великих кроків. Усередині actions перевіряється готовність
конкретного елемента та результат дії. `waitForUiReady` чекає видимий, доступний,
стабільний вузол без ознак завантаження; після цього action повторно шукає handle.
Заміна React-вузла перезапускає коротке очікування стабільності.

About зберігає наявний сканер форм і результатів, додає стабілізацію цільових станів,
діагностику до закриття помилок та обмежені спроби пошуку підказок. Скорочення тексту
обмежене вісьмома спробами і бюджетом `timeout` на поле. Зникнення Work/College-форми
вважається успіхом лише разом з появою ознаки збереженого запису.

Фіксовані багатосекундні паузи перед кліками й preview замінені очікуванням стану.
Короткі паузи руху миші, прокрутки та введення збережені. Наявна пауза перед
перезапуском профілю після невдалої зміни імені теж збережена.

## Як додати модалку

Обробники залишаються у `facebook/modals`; інструкції — у `facebook/modals/AGENTS.md`.
Журнал не виконує інструкції з тексту сторінки й не генерує обробники автоматично.

| Стан | Обробник |
| --- | --- |
| Review audience | `reviewAudience.js` |
| Who can see your future posts | `futurePostsAudience.js` |
| Захист акаунта | `accountProtection.js`, наявний recovery-workflow |
| Leave Page / Invalid Name в About | локальні обробники About зі знімком до закриття |
| Невідоме вікно | запис доказів і помилка після вичерпання очікування |

Для нового випадку спочатку переглянути зразок із підсумку. Додати лише підтверджені
UI-тексти у мовні словники, селектори — у `facebook/selectors`, а `match`/`handle` —
у реєстр відповідного контексту. В обробнику перевіряти очікуваний результат.
Очищений зразок можна додати до mock-тесту, обов’язково перевіривши інший регістр
і відмову на схожому, але іншому вікні. Невідоме вікно поверх композера не вважається
готовим композером лише тому, що він теж присутній у DOM.

## Перевірки

Нові тести включені у `npm run test:all`: журнал, приватність даних знімка,
видалення повторів, ліміти, помилки диска, ізоляція сторінок, очікування UI
та підключення всіх шести кроків workflow.

Додаткова перевірка на локальній HTML-сторінці: `node test/testBrowserTraceBrowser.js`.
Вона використовує окремий тимчасовий профіль Chrome/Edge без Facebook і AdsPower.
Можна вказати дозволений браузер через `CHROME_PATH`; системна політика має дозволяти
його запуск із remote debugging. До загального набору ця перевірка не входить.
