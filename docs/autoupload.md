# Автозаливи

## Оновлення access token API-клієнтів і БМ

Кнопка з ключем праворуч від синхронізації AdsPower одразу виконує HTTP-операцію
через IPC, без створення фонової задачі та додавання до черги. До завершення
кнопка показує індикатор; повторний виклик для того самого клієнта блокується.
`services/accounts/refreshFacebookAccessToken.js` використовує збережені cookies і
User-Agent клієнта та його режим проксі. Екшен `getAdsManagerSession` із
`refreshSession: true` читає HTML Ads Manager одним GET (крім переходів і повторів
після мережевих збоїв), перевіряє власника сесії та отримує EAAB-токен.
Браузер, домашня сторінка Facebook і списки активів не завантажуються.
Оновлюється лише access token; при помилці попередній токен зберігається.
Після збереження токена виконується наявна перевірка API-клієнта через Graph API
`/me?fields=id,name`, без синхронізації AdsPower та читання списків активів.
Результат перевірки оновлює статус клієнта в GUI. Неактивний токен або помилка
перевірки показують попередження; отриманий токен залишається збереженим.
HTTP-історія приєднується до звіту операції без значень токенів та cookies.

## Оформлення комент-акаунтів

`workflows/accounts/executeCommentAccountAutouploadSetupWithProfile.js` працює
без браузера через cookies, UA і проксі профілю або призначену проксі воркера.
Використовує легкий `checkProfileSession`, без Ads Manager і списків активів.
Початковий GET одночасно перевіряє сесію та читає runtime. Власник звіряється
з `c_user` і `ACCOUNT_ID`, поточний actor — із власником. При активній фанці
наявна mutation перемикає контекст на соца, потім один GET підтверджує actor
та оновлює Facebook-сесію. Помилка авторизації зупиняє оформлення.

Accounts Center отримує окремий контекст через `prepareNameContext`;
`executeNameChange` отримує готову сесію та не завантажує її повторно.
Невдала зміна імені зберігає помилку та наявний тег Change Name Error,
але незалежні дії продовжуються. Профіль у такому разі має результат `failed`.
Далі виконуються аватар, обкладинка, очищення постів, послідовне створення
фото-постів із датуванням та About: очищення біо, робота (компанія й посада), освіта.
Налаштування About, очищення біо та країни довідників доступні також для автоаплоаду.

Workflow передає спільний `HttpActionContext` у HTTP-обгортки через `options.context`.
Для самостійного запуску обгортка створює контекст і викликає `prepare()`;
основні API-екшени отримують готовий транспорт. `readRuntime()` лише повертає
підготовлені параметри та не виконує прихованого GET. Контекст повторно
використовується лише з тим самим клієнтом і сесією; після перемикання actor
створюється новий. Прострочена сесія оновлюється перед наступною дією.

`actionDelaySeconds` задає базову паузу, початково 30 секунд. Перед кожною
наступною логічною дією додається незалежна випадкова поправка ±5 секунд,
із нижньою межею 0. Створення поста і зміна його дати — одна дія без паузи
всередині; після останньої дії та перед вимкненими кроками очікування немає.
Для About очікування виконується тільки перед першою mutation логічного етапу.
Читання поточного біо, пошук компанії, посади чи закладу не запускають паузу.
Поточне біо читається запитом редактора `ProfileCometBioTextEditorPrivacyIconQuery`
(`doc_id=23931151619841616`, `variables.id` — поточний actor) зі шляху
`data.user.profile_intro_card.bio.text`. Явне `bio: null` означає порожнє поле;
відсутня картка, поле або невідомий формат не вважаються порожнім біо.
Порожнє біо пропускається без mutation та паузи; невідомий формат відповіді
записується як помилка читання. Оновлення компанії й посади, включно з видаленням
попередньої роботи, виконується разом. Освіта завершує сценарій без кінцевої паузи.

Після успішного імені часткові невдачі дають `completed_with_error`
(успіх із попередженнями). Звіт містить результати кроків і кожного поста,
доступні HTTP/GraphQL-коди та безпечний текст Facebook.
Звичайна помилка кроку, зокрема видалення постів, не заважає наступним етапам;
явна GraphQL-відмова не прирівнюється до невідомого результату запису.
Втрата авторизації,
невідповідність actor і невизначений результат запису зупиняють наступні зміни.
POST автоматично не повторюється. Перейменування AdsPower, теги статі,
папки фото й запис статистики використовують спільну логіку оформлення.

Перевірка: `node --test scripts/comment-account-autoupload.test.js`.

Вкладка зберігає локальний список AdsPower-профілів для роботи з Facebook через HTTP без запуску браузера. Доступні перевірка сесії та надсилання заявок у друзі. Перевірка сесії не змінює акаунт; надсилання заявки є окремою дією.

## Використання

### HTTP-екшен списку фанок

`facebook/autoupload/actions/pages/getFanPages.js` експортує
`getFanPages(client, { signal } = {})`. Аргумент `client` — наявний
`FacebookWebClient`, створений із cookies, User-Agent та проксі профілю.
Попередній `checkSession()` не потрібен: екшен сам читає актуальний контекст
і підтримує як соца, так і поточну фанку.

```js
const result = await getFanPages(client, { signal });
// { success, outcome, code, message, accountId, currentActorId, pages, count }
// pages: [{ additionalProfileId, name, photoUrl }]
```

ID соца визначається з чинної Facebook cookie `c_user` і звіряється з
`ACCOUNT_ID` у HTML. Поточний actor читається з актуальної відповіді Facebook.
Через окремий `HttpProfileReadContext` перевикористовується
`CometProfileSwitcherListQuery` браузерного API-екшену. Поточний actor із назвою
та аватаркою додається до списку, соц видаляється, дублікати прибираються за ID.
Перевірки типу профілю немає: усі профілі, крім соца, вважаються фанками.
За відсутності назви чи аватарки відповідне поле дорівнює `null`.

Екшен виконує лише читання, не перемикає профіль і не зберігає сесію на диск.
`checkSession()` зберігає фактичний контекст відповіді Facebook: фанку або соца.
Власник перевіряється за `c_user` та `ACCOUNT_ID`; `i_user` не видаляється,
автоматичного перемикання та додаткового GET для переходу на соца немає.
Сесія містить `accountId` власника та `FacebookID` поточного actor; `getFbData()`
повертає `accountId`, `actorId` та сумісний із соціальними діями `userId` власника.
Обидва контексти зберігаються й відновлюються без підміни actor.
Поточні соціальні екшени при активній фанці повертають
`FACEBOOK_SOCIAL_CONTEXT_REQUIRED` до запиту операції. Перевірка актуальності
кешованої сесії використовує `validateFbData(..., { allowPageActor: true })`.
`getFanPages()` читає список у будь-якому з цих контекстів.
Помилка не повертається як успішний порожній список; формат невдачі — стандартний
`actionFailure`. Cookies, HTML і токени в результат не включаються.
Автоматичної пагінації немає; повертаються профілі, отримані цим query.
У GUI список завантажується кнопкою «Отримати список фанок» у модалці
«Пошарити фанку», доступній із меню «Дії» для одного вибраного профілю.

Перевірка: `node --test scripts/autoupload-pages.test.js`.

### HTTP-workflow видачі повного доступу до фанки

`facebook/autoupload/workflows/grantFanPageAccess.js` експортує
`grantFanPageAccess(client, { additionalProfileId, targetUserId, password, signal, onStage })`.
Це HTTP-flow без Puppeteer; сесія залишається у фактичному контексті вибраної фанки.

Послідовність: читання сесії → перемикання через наявний API-екшен, якщо потрібно →
підтвердження actor → читання доступів → шифрування → reauth → інвайт → контрольне читання.
Уже наявний повний доступ або запрошення пропускають шифрування та mutation видачі доступу.
ID фанки — саме `additionalProfileId` зі списку перемикання, а не довільний Graph Page ID.

- `HttpPageActionContext` централізує runtime і transport чотирьох GraphQL-операцій;
  зміна actor оновлює стан HTTP-клієнта, не записуючи cookies в AdsPower.
- `actions/pages/` містить `switchToFanPage`, `getFanPageAdminPermissions`,
  `reauthFanPageAdmin`, `inviteFanPageAdmin`. Перемикання й інвайт перевикористовують
  браузерні API-екшени через явний HTTP-транспорт.
- `encryption/FacebookPasswordEncryption` завантажує актуальний
  `FBBrowserPasswordEncryption` і його залежності зі startup JS-ресурсів Facebook.
  CDN-запити йдуть через ту саму проксі без cookies. Модулі виконуються в окремому
  JS-контексті з Web Crypto; завантажений код і пароль не записуються на диск.
  Ресурси читаються послідовно. Тимчасовий TLS/мережевий обрив GET має ліміт
  чотири спроби; після TLS close-notify використовується TLS 1.2 зі звичайною
  перевіркою сертифіката. Це обходить відтворений збій Electron на Facebook CDN.
  У пам’яті процесу кешуються фабрики модулів за URL до 48 ресурсів, без паролів,
  токенів або згенерованих криптоключів. Невдале завантаження не кешується.
  Якщо залежності більше не доступні у цих ресурсах, workflow повертає
  `FACEBOOK_ENCRYPTION_MODULE_UNAVAILABLE` до надсилання пароля.
  Результат невдачі містить безпечний `encryptionDiagnostics`: кількість ресурсів,
  коди транспортних збоїв, типи помилок розбору та назви відсутніх модулів.
- `workflows/autoupload/grantProfileFanPageAccess.js` приймає `adsPower`, один із
  `profileId` / `profileNo`, `additionalProfileId`, `targetUserId`, `signal`, `onStage`.
  Готує клієнт наявним `checkProfileSession` і бере пароль із `profile.password`,
  як «Персональні акаунти». Зовнішні інтеграції не входять до Facebook-workflow.

Публічний результат містить `success`, `outcome`, `stage`, `accountId`,
`additionalProfileId`, `targetUserId`, `inviteSent`, `invitePending`, `outcomeUnknown`.
Контрольне читання додає `verified` і `hasFullControl`. `INVITE_SENT` означає
прийняття запрошення Facebook, а не його прийняття користувачем.
`INVITE_ALREADY_PENDING` та `FULL_CONTROL_ALREADY_PRESENT` не створюють нового інвайту.

Після таймауту інвайту виконується лише контрольне читання. Знайдене запрошення або
повний доступ дають `INVITE_CONFIRMED`; інакше зберігається невизначений результат
без повторної mutation. Якщо Facebook уже підтвердив надсилання, але контрольне
читання не вдалося, результат залишається `INVITE_SENT` з `verified: false`.
Сирі помилки, пароль, зашифрований пароль і токени не входять до результатів чи логів.

Ручний запуск, який може надіслати інвайт із повним доступом:

```text
node scripts/manual/grantFanPageAccess.js --profile-no NUMBER --page-id ADDITIONAL_PROFILE_ID --target-user-id USER_ID
```

Замість `--profile-no` можна передати `--profile-id`. Скрипт друкує тільки етапи
та безпечний результат. Перевірка: `node --test scripts/autoupload-page-access.test.js`.

У вкладці «Автозаливи» виберіть один профіль → «Дії» → «Пошарити фанку».
Список читається лише за кнопкою; відсутня або застаріла сесія готується
наявним `checkProfileSession`, без браузера. Під кнопкою введіть UID отримувача.
Кожен рядок містить аватарку, назву, additional profile ID та кнопку «Пошарити».
Область списку вміщує п’ять рядків на звичайній висоті вікна, решта доступні
внутрішнім скролом; на низьких вікнах область зменшується.

Результат з’являється внизу зеленим або червоним текстом. Модалка залишається
відкритою для наступних фанок; отримувач і закриття блокуються лише під час запиту.
Успішні й невизначені результати блокують повтор кнопки для тієї самої пари
фанка/отримувач у відкритій модалці. Сервер перевіряє одного вибраного профіля,
UID отримувача та належність фанки до отриманого списку. Операції одного профілю
серіалізуються, пароль читається з AdsPower лише backend-частиною.

IPC `autoupload:fan-pages` і `autoupload:share-fan-page` повертають безпосередній
результат у модалку. Шеринг записується до журналу як `fan-page-share`;
оновлений валідний знімок сесії зберігається через зашифроване сховище.

### Робота у вкладці

1. У вкладці «Акаунти під коментарі» виберіть профілі та натисніть «Додати до автозаливів».
2. Виберіть локальну групу або створіть нову. За замовчуванням використовується «Нові».
3. У вкладці «Автозаливи» виберіть профілі й натисніть «Перевірити сесію».
4. Перебіг видно у фонових задачах, результат — у таблиці, журналі перевірок і вікні «Деталі».

Кнопка біля номера профілю відкриває його браузер AdsPower та стає червоною. Повторне натискання закриває браузер; якщо його вже закрили вручну, кнопка просто повертається у звичайний стан. Під час відкриття вкладки та натискання «Оновити» стан браузерів перевіряється через наявні методи GUI-сервісу.

Групи цієї вкладки не змінюють групи AdsPower. Один профіль належить одній локальній групі; повторне додавання оновлює назву та групу без дублювання. Видалення групи переносить її профілі в «Нові». Прибирання зі списку не видаляє профіль AdsPower. Журнал зберігає останні 500 результатів.

## Дані та межі модулів

### HTTP-дії соціального профілю

У меню «Дії» доступні аватарка, обкладинка, очищення постів, фото-пости з минулою датою, Bio та освіта/робота. Введені дані застосовуються до кожного вибраного соціального профілю. Для очищення постів потрібне підтвердження у формі. Публікація створює окремий публічний пост для кожного фото, з необов’язковим текстом, після чого змінює його дату на вказану (час 12:00). Якщо зміна дати не вдалася, уже опублікований пост не видаляється автоматично; його ID та стан залишаються в деталях результату.

| Екшен у `facebook/autoupload/actions/profile/` | Перевикористана реалізація |
| --- | --- |
| `changeProfilePicture.js` | `api-actions/profile/changeProfilePicture.js`: upload, crop та встановлення фото |
| `changeCoverPhoto.js` | `api-actions/profile/changeCoverPhoto.js`: upload та встановлення обкладинки |
| `clearProfilePosts.js` | `api-workflows/profile/clearProfilePosts.js`: читання всіх сторінок Manage Posts, видалення звичайних і приховування системних постів, перевірка залишку |
| `publishProfilePostsWithDates.js` | `api-workflows/profile/publishProfilePostsWithDates.js`: upload → створення story → зміна дати |
| `updateBio.js` | `api-actions/updateBio.js`: встановлення або очищення Bio |
| `updateAbout.js` | `updateEducationField` / `updateWorkField` з `api-workflows/profile/fillProfileAbout.js`: College та робота |
| `getAboutSectionTokens.js` | `api-actions/getAboutSectionTokens.js`: свіжі токени конкретної секції |

Порядок виконання:

1. IPC `autoupload:profile-action` перевіряє `{ ids, action, input }`, резервує профілі та повертає `{ taskId }`.
2. `AutouploadService.runProfileAction` відновлює готову базову сесію зі сховища. Відсутня або застаріла сесія завершує дію без запуску браузера; спочатку потрібна перевірка сесії.
3. `runProfileAction.js` запускає дію в черзі клієнта та створює новий `HttpActionContext` тільки для цього виклику. Контекст через HTTP читає актуальний runtime соціального профілю, звіряє actor із збереженою сесією та використовує cookies, UA й проксі наявного `FacebookWebClient`.
4. Для зміни Bio `getAboutSectionTokens.js` заново запитує `directory_intro`. Під час очищення з `skipIfEmpty` спочатку читається поточне біо через запит редактора; якщо воно порожнє, токени секції та mutation не запитуються. Для освіти й роботи окремо запитуються `directory_education` та `directory_work`. `collectionToken`, `sectionToken` і `rawSectionToken` передаються у наступні запити тільки всередині поточної дії. Між діями вони не кешуються та не зберігаються на диск.
5. Core API-екшени отримують явний HTTP-транспорт через `api/actionTransport.js`. Він виконує form-urlencoded і multipart-запити, тому Puppeteer та відкриття браузера не потрібні. Браузерні виклики цих самих екшенів працюють через попередній транспорт.
6. У журнал записуються лише статуси, коди помилок, лічильники та ID створених постів. HTML, cookies, токени й сирі GraphQL-відповіді у GUI та звіт не передаються. Часткове виконання не маскується успіхом.

About змінює лише заповнені поля: перший запис College оновлюється або створюється, для роботи спочатку додається новий запис і після успіху видаляється перший попередній. Випадковий fallback для освіти та роботи вимкнено. Bio має окрему дію; порожнє значення очищує Bio. Education mutation не додає `logging_data.nav_chain`.

Дії не отримують додаткових токенів під час загальної перевірки сесії. Для публікацій немає постійного кешу колекцій: кожен запуск заново читає runtime, upload ID створюється для нового фото, story ID береться з відповіді створення, cursor Manage Posts — з поточного читання. Accounts Center залишається окремим контекстом тільки для зміни імені.

Mutation, включно з `useProfileCometEducationExperienceSaveMutationQuery`, не повторюються автоматично при мережевій помилці. Невизначений результат блокує наступні запити поточної дії. Checkpoint або втрата авторизації інвалідують сесію. Перед ручним повтором перевірте фактичний стан профілю.

Локальна перевірка: `npm run test:autoupload`, GUI — `npm --prefix frontend run test -- src/test/autoupload.test.jsx`. Одноразовий живий тест профілю 2333: `node scripts/manual/testAutouploadProfileActions.js --execute-profile-2333`. Він змінює тестовий профіль і відмовляється повторювати запуск, якщо вже є звіт `data/reports/autoupload-profile-2333-live.json`. Режим `--inspect-profile-2333` лише читає стан тестової публікації.

### Зміна імені соціального профілю

Виберіть профілі → «Дії» → «Змінити ім’я соціального профілю (HTTP)». У модальному вікні вкажіть ім’я, прізвище та за потреби друге ім’я. Введені дані застосовуються до всіх вибраних профілів. Дія змінює особистий Facebook-профіль; назва AdsPower-профілю та назви фанпейджів залишаються окремими даними.

IPC `autoupload:change-name` приймає `{ ids, firstName, middleName, lastName }` та повертає `{ taskId }`. Задача послідовно виконує `facebook/autoupload/actions/accounts/changeFacebookName.js` через збережену HTTP-сесію і проксі клієнта, без запуску браузера. Сесія має бути актуальною; за відсутньої або застарілої сесії потрібно повторити «Перевірити сесію».

Екшен читає HTTP-сесію Accounts Center, перевіряє відповідність поточному userId, доступність зміни та валідність імені, а потім виконує `useFXIMUpdateNameMutation`. Doc ID, змінні й шлях підтвердження взято з наявних `api-actions/accounts`. Запис не повторюється автоматично. Невизначений результат вимагає перевірки фактичного імені у Facebook. Результати з операцією `profile-name-change` відображаються в журналі та деталях профілю; cookies, HTML і токени туди не записуються.

- `classes/AdsPower.js`: єдина точка доступу до AdsPower. Методи `getProfileById`, `getProfileCookies`, `getProfileUserAgent`, `getProxyById` використовують наявну чергу запитів.
- `facebook/api/FacebookWebClient.js`: окремий клієнт одного профілю; cookies, UA, HTTP через `ProxyHttpClient`, перенаправлення та перевірка сесії. Секретний стан приватний.
- `facebook/session/parseWebSession.js`: виділення полів із HTML. Відсутність поля означає помилку перевірки, а не автоматичний висновок про блокування акаунта.
- `workflows/autoupload/checkProfileSession.js`: підготовка клієнта з актуальних даних AdsPower та безпечний результат перевірки.
- `services/autoupload/AutouploadStore.js`: версійоване локальне сховище з послідовним атомарним записом; пошкоджений JSON не перезаписується.
- `workflows/autoupload/refreshProfileSession.js`: повна перевірка Facebook, Ads Manager, access token, рекламних кабінетів і фанпейджів.
- `facebook/autoupload/actions/getAdsManagerSession.js`: отримання сесії Ads Manager та EAAB-токена через HTTP.
- `services/autoupload/AutouploadSessionStore.js`: атомарне збереження зашифрованих сесій окремо для кожного профілю.
- `services/autoupload/AutouploadService.js`: локальні групи, профілі, результати та відновлення клієнтів зі збережених сесій.
- Electron IPC `autoupload:get`, `autoupload:mutate`, `autoupload:check`, подія `autoupload:updated`: містять лише метадані та безпечні результати.

`data/autoupload/workspace.json` містить групи, ID/номер/назву профілю, його локальну групу, статуси, рекламні кабінети, фанпейджі та безпечні результати. У таблиці перед номером AdsPower показано індикатор акаунта, після назви — кабінети з окремими індикаторами та фанпейджі. Окремі колонки статусу сесії та останньої перевірки прибрано; діагностика залишається в деталях і журналі.

Cookies з атрибутами, UA, проксі, параметри Facebook і Ads Manager та access token зберігаються окремо в `data/autoupload/sessions/`. Файли шифруються через Electron `safeStorage` і прив’язані до облікового запису Windows. За відсутності системного шифрування запис відхиляється. Увесь `data/autoupload/` виключений із Git. Секрети не передаються до React і не потрапляють у журнал.

Повторна перевірка видаляє попередню сесію та заново отримує всі дані. Часткова помилка, наприклад відсутність прав на фанпейджі, показується окремим попередженням. Наступні дії відновлюють збережений HTTP-клієнт без повторного читання AdsPower. Перевірка актуальності параметрів вебсесії обмежена 15 хвилинами; після цього потрібна нова перевірка. Виявлення Login або Checkpoint під час запиту змінює індикатор акаунта та видаляє недійсну збережену сесію. Технічна помилка не означає автоматично бан акаунта.

Кожна перевірка заново читає дані AdsPower. HTTP-клієнт використовує лише проксі цього профілю; без налаштованої проксі операція завершується помилкою. Немає переходу на пряме з’єднання. Cookies враховують домен, шлях, строк дії та Secure; Set-Cookie застосовується між переходами. Дозволені лише HTTPS-переходи всередині facebook.com. Значення токенів та HTML не потрапляють у результати.

## Розширення

Нові HTTP-дії додаються як методи `FacebookWebClient` або окремі модулі, викликані цими методами. Для зміни стану клієнта використовується `run()`, що серіалізує операції одного екземпляра. Підготовка профілю та складна послідовність дій залишаються у workflow. Масові операції запускаються через наявний `BackgroundTaskManager` із ресурсом `adspower-profile:<номер>`; це запобігає одночасній роботі задач над одним профілем. Перевірка зараз виконує профілі послідовно.

Вебсесія не замінює Graph API access token. Для поточних Graph API функцій залишається `FacebookGraphApi`.

## Заявки в друзі

Виберіть профілі, натисніть «Додати в друзі», введіть числовий Facebook ID отримувача та натисніть «Надіслати заявки». Профілі виконуються послідовно зі збереженими сесіями. Якщо сесія відсутня або застаріла, спочатку потрібна перевірка профілю. Одна відмова не зупиняє решту профілів; скасування фонової задачі припиняє перехід до наступного профілю.

Структура дій:

- `facebook/autoupload/actions/friends/sendFriendRequest.js` — функція `sendFriendRequest(fbData, targetUserId, options)` і опис mutation.
- `facebook/autoupload/graphql/buildForm.js` — службові поля GraphQL із поточної сесії.
- `facebook/autoupload/graphql/parseResponse.js` — XSSI-префікс, JSON/NDJSON, помилки верхнього рівня та `data.errors`.
- `facebook/autoupload/graphql/errors.js` — безпечні повідомлення й формат діагностики, сумісний за полями з API-клієнтами.

`client.getFbData(profileId)` повертає backend-об’єкт `{ profileId, userId, session, client }`. Сесія містить токени, а клієнт тримає cookies, UA та проксі. Цей об’єкт не можна записувати в журнал або серіалізувати для GUI. Для збереження використовується тільки `client.exportSession()` через зашифроване сховище, для відновлення — `FacebookWebClient.restore()`. Дані старого об’єкта відхиляються після оновлення сесії; також перевіряється строк актуальності. `lsd` отримується з актуального HTML. Якщо потрібного поля немає, POST не виконується.

Успіх підтверджується лише відповіддю потрібного отримувача з `friendship_status === OUTGOING_REQUEST`, без GraphQL-помилок і з HTTP 2xx. Це означає вихідну заявку, а не вже підтверджену дружбу. HTTP 200 та `is_final` окремо не є підтвердженням.

Результат містить `success`, `outcome`, `message`, `code` застосунку, фактичні `httpStatus`, `graphCode`, `graphSubcode`, `apiErrorCode`, `traceId`, `metaRequestId`, список безпечних помилок, `actionRequired`, `outcomeUnknown` і `retryable`. Відсутні коди Facebook залишаються `null`. Стан акаунта показує індикатор перед номером, результат дії — колонка «Остання дія»; повна діагностика доступна в деталях профілю.

POST не повторюється при timeout або втраті відповіді й не пересилається повторно після redirect. Перед POST у локальному сховищі записується невизначений результат спроби для пари профіль/отримувач. Якщо програма завершиться в цей момент, наступна задача не повторить запит автоматично. Підтверджена раніше заявка також не надсилається вдруге. Для невідомого результату потрібно перевірити фактичний стан дружби; автоматичного зняття цієї позначки в інтерфейсі поки немає.

Використовується `FriendingCometFriendRequestSendMutation` з `doc_id` із наданого HAR. Це не гарантує актуальність mutation: Facebook може змінити doc_id або вимагати додатковий контекст. Непідтверджені `click_proof_validation_result` не генеруються. Старі cookies та токени HAR не використовуються. Реальне надсилання перевіряється запуском користувача; локальні тести використовують лише mock-відповіді.

## Вхідні заявки та прийняття

Нові backend-дії доступні з `facebook/autoupload/actions/friends/index.js`:

```js
const fbData = client.getFbData(profileId);
const incoming = await getIncomingFriendRequests(fbData, { signal });
const accepted = await acceptIncomingFriendRequest(fbData, targetUserId, { signal });
```

- `getIncomingFriendRequests(fbData, options)` спочатку використовує `FriendingCometRootContentQuery`, а за відсутності придатної відповіді читає JSON із `script[type="application/json"]` сторінки `/friends`. JavaScript сторінки не виконується. Опція `source` може мати значення `auto`, `graphql` або `html`.
- `acceptFriendRequest(fbData, targetUserId, options)` виконує лише mutation прийняття конкретної заявки. Цей метод призначений для вже перевіреного отримувача.
- `acceptIncomingFriendRequest(fbData, targetUserId, options)` перевіряє поточний список і приймає лише знайдену заявку зі статусом `INCOMING_REQUEST`. Читання та прийняття виконуються в одній черзі клієнта без взаємного блокування.

Отримання повертає `success`, `totalCount`, `loadedCount`, `requests` з полями `id`, `name`, `status`, а також `hasNextPage`, `endCursor`, `incomplete`, `source` і безпечну діагностику. Порожній масив `edges` є успішним результатом, а відсутній `edges` — помилкою. Сторінки не підвантажуються за вигаданими параметрами курсора. Якщо `hasNextPage === true`, інформації про пагінацію немає або загальна кількість перевищує завантажену, встановлюється `incomplete: true`.

Відсутність потрібного ID у неповному списку повертає `FACEBOOK_INCOMING_REQUESTS_INCOMPLETE`, а не висновок про відсутню заявку. Якщо ID знайдено, можна прийняти саме цю заявку навіть за неповного списку. Масового прийняття немає.

Успіх прийняття потребує HTTP 2xx, відсутності GraphQL errors, збігу `friend_requester.id` із потрібним ID та `friendship_status === ARE_FRIENDS`. Повертається `FRIEND_REQUEST_ACCEPTED`; помилки мають той самий формат діагностики, що й надсилання. Mutation не повторюється після timeout чи невідомого результату. `beforeSend`, як і в надсиланні, дозволяє workflow зберегти позначку спроби перед POST.

Використовуються doc_id з наданого опису HAR. Застарілі сесійні значення, ID акаунтів із прикладів і вигадані результати перевірки кліку не використовуються. Якщо сервер потребуватиме додаткового актуального контексту, метод поверне помилку; автоматичного запуску браузера для обходу HTTP-помилки немає. Ці дії поки є backend-функціями: нові кнопки чи масові операції GUI не додаються.

## Admin-доступ до рекламного кабінету

Backend-екшени розміщені в `facebook/autoupload/actions/adAccounts/` та експортуються через `index.js`:

- `findFriendById(fbData, targetUserId, options)` читає `payload.entries` з Ads Manager `first_degree.php`, шукає точний UID із `is_friend_or_self === true` та виключає самого власника. Відсутність у відповіді не доводить відсутності дружби: список може бути обмежений сервером.
- `getAdAccountUsers(fbData, adAccountId, options)` читає користувачів РК через `adsmanager-graph.facebook.com/v22.0/act_{id}`. Повертає лише UID, роль, permissions та ознаку Admin. За наявності наступної сторінки повертає `incomplete: true`, не переходячи за невідомими посиланнями.
- `shareAdAccount(fbData, adAccountId, targetUserId, options)` виконує пошук друга, перевірку наявного доступу, один POST `/act_{id}/users` з `uid` та роллю `281423141961500`, а потім повторне читання прав. Успіх потребує одночасно `success: true` у POST та потрібного UID з `role: 1001` і permissions `1,2,3,4,5,7` у відповіді перевірки. Наявний підтверджений Admin повертає `AD_ACCOUNT_ALREADY_ADMIN` без POST. Неповний список без знайденого Admin блокує зміну.

Усі запити виконуються з чинними cookies, UA та проксі того самого `FacebookWebClient`. Збережена сесія Ads Manager обов’язкова. GET пошуку друзів передає `__a=1`, `__user`, `__req` і актуальні `fb_dtsg_ag`, `lsd`, `jazoest`, `__rev` із сесії Ads Manager. Запити лише до `https://adsmanager-graph.facebook.com` отримують чинний EAAB у заголовку `Authorization: Bearer ...` через `client.requestAdsManagerGraph()`; у URL чи тілі POST токен не передається. Метод відхиляє інший origin.

Динамічні `_sessionID`, flowlet і `xref` не вигадуються та не копіюються з HAR. У живій перевірці надання Admin спрацювало без цих полів; це не гарантує однакової поведінки для всіх профілів і майбутніх версій Meta. UI-запит `add_user_confirm`, який у HAR був після успішного призначення, не виконується: фактичний результат перевіряється читанням користувачів РК.

Викликаючий GUI має спочатку показати користувачу конкретний РК, отримувача та роль Admin й отримати явне підтвердження. Лише після нього передається об’єкт із точними нормалізованими ID:

```js
const result = await shareAdAccount(fbData, adAccountId, targetUserId, {
    signal,
    confirmation: { confirmed: true, adAccountId, targetUserId, role: "ADMIN" },
    beforeSend: async (intent) => persistPendingOperation(intent),
});
```

`beforeSend` записує намір зміни в `AutouploadStore` до POST. Незавершений або невизначений результат зберігається після перезапуску й блокує повторний POST; якщо читання прав уже підтвердило Admin, операція завершується без повторної зміни. Без об’єкта підтвердження, при невідповідності його ID або ролі повертається `FACEBOOK_ADMIN_CONFIRMATION_REQUIRED` без запитів. При timeout, redirect чи збої перевірки після POST повертаються `outcomeUnknown`, `retryable: false` та `actionRequired: check_ad_account_permissions`; автоматичного повтору POST немає. При Login/Checkpoint потрібно спочатку відновити авторизацію. Секрети та повні відповіді не повертаються в результати.

У вкладці «Автозаливи» виберіть профілі та натисніть «Пошерити РК». Модальне вікно показує збережені персональні РК цих профілів, згруповані за профілем, з окремими перемикачами. Кабінети з бізнес-власником не показуються. Для записів старого формату без ознаки `isPersonal` потрібна нова перевірка сесії; вона зберігає `isPersonal` і `businessId`. Введіть Facebook ID отримувача, виберіть кабінети й підтвердьте повний Admin-доступ. Зміна отримувача або набору РК скидає підтвердження.

IPC `autoupload:share-ad-accounts` перевіряє належність вибраних РК до вибраних профілів і до збережених персональних кабінетів, відхиляє дублікати та запускає фонову задачу. РК обробляються послідовно через збережені сесії, із блокуванням відповідних AdsPower-профілів. Результат кожного РК потрапляє в журнал операцій і деталі профілю окремо від заявок у друзі. У разі часткової невдачі інші РК продовжують оброблятися; скасування зупиняє наступні операції.

Перевірено mock-тестами та однією явно підтвердженою користувачем живою операцією: POST повернув `success: true`, наступний GET підтвердив отримувача з роллю 1001 та всіма потрібними permissions. Порожня відповідь має код `FACEBOOK_RESPONSE_EMPTY`; помилки містять етап (`friends_lookup`, `ad_account_users`, `ad_account_admin_write`), Content-Type та кількість байтів без сирого тіла відповіді.

## Сумісність

Потрібен запущений AdsPower Local API з доступом до профілів та актуальним патчем, який підтримує cookies й UA API. Браузер профілю не запускається. Якщо AdsPower не повертає збережені cookies закритого профілю, перевірка завершується помилкою. Автоматичного обходу через запуск браузера немає.

Facebook може змінити формат HTML або вимагати авторизацію/підтвердження. UA, cookies та проксі не відтворюють повний мережевий і браузерний відбиток. Успішна підготовка сесії підтверджує лише поточну перевірку, а не роботу всіх майбутніх дій.

Джерела: [AdsPower cookies API](https://localapi-doc-en.adspower.com/docs/Query-profile-cookies), [AdsPower API, включно з POST UA](https://documenter.getpostman.com/view/45822952/2sB34hEzQH), [підхід fbchat-v2](https://github.com/m008v/fbchat-v2/blob/main/src/_core/README.md). Python-бібліотека не встановлюється; клієнт реалізований у Node.js.

## Передача персональних РК кінгу

Виберіть донорів і натисніть «Передати персональні РК кінгу». У модальному вікні виберіть групу та профіль кінга з автозаливів. Список окремих РК обирати не потрібно: операція використовує повні збережені списки `assets.adAccounts` донорів і кінга. Порівняння відбувається за `accountId`, історія шерингу не замінює список кінга. Донори без відсутніх у кінга персональних РК пропускаються без заявок у друзі та без підготовки сесій.

Сесії використовуються лише з пам'яті або локального сховища: автоматичного повторного збору сесій чи списків РК немає. Для кожного потрібного донора надсилається заявка кінгу, на кінгу перевіряються вхідні заявки й виконується прийняття навіть за помилки перевірки або відсутності заявки у відповіді. Потім відсутні РК передаються окремими POST без додаткового читання друзів чи користувачів РК. Успіх означає `success: true` у відповіді Facebook (`writeAccepted: true`, `verified: false`), без окремого контрольного читання прав. Після успіху РК одразу додається до локального списку кінга для наступних донорів і запусків. Невизначений результат POST зберігається та блокує сліпий повтор. Результати надсилання, прийняття, пропуску та передачі з кодами й безпечним текстом помилки доступні в журналі та деталях відповідного профілю.

Олівець біля назви змінює назву в AdsPower та автозаливах. Червоне відро праворуч прибирає профіль після підтвердження. Галочка «Також видалити профілі в AdsPower» початково вимкнена. Відмова AdsPower не прибирає відповідний профіль із локального списку. Видалення проходить через `AdsPower.deleteProfile()` і спільну чергу запитів, використовуючи документований [Delete Profile API](https://localapi-doc-en.adspower.com/docs/YCyJxM).

## Локальна перевірка

Помилки перевірки містять `diagnostic`, а часткові оновлення — `warnings[]` з окремими `status`, `code`, `networkCode`, `httpStatus`, `graphCode`, `graphSubcode`, `message`, `stage`, `endpoint`, `method` і `durationMs`. Типи розрізняють timeout, мережевий збій, недоступність або авторизацію проксі, HTTP 403/429 та інші HTTP-помилки, Facebook API, Login/Checkpoint, відсутність токена й невідповідність акаунта. Основний статус акаунта залишається окремим: активна Facebook-сесія може мати попередження Ads Manager.

Серверний текст помилки з JSON або `text/plain` зберігається після видалення секретів. Загальний лог містить лише компактну діагностику без payload, HTML та заголовків; URL у ньому містить origin і path. Повні діагностичні дані HTTP-автозаливів зберігаються окремо за правилами нижче. Невідомі внутрішні винятки без безпечного повідомлення повертають загальний текст. Початковий код мережі зберігається навіть після `PROXY_POOL_EXHAUSTED` або невизначеного результату POST. Причини потрапляють у загальний журнал через події `http.request.failed`, `autoupload.http.failed`, `autoupload.session.failed`, `autoupload.ads-manager.failed`, `autoupload.assets.failed` і `autoupload.action.failed`, а також у деталі профілю. Автоматичні повтори mutation не додаються.

## Історія HTTP-запитів і звіти

Публічні HTTP-екшени зберігають попередні поля результату (`success`, `outcome`, коди, лічильники тощо) та додатково повертають `actionId` і `exchanges[]`. Запис містить фактичний метод, URL, заголовки й тіло запиту, HTTP-статус, заголовки й тіло відповіді, час, тривалість та мережеву помилку. GraphQL form-поля, `doc_id`, назва операції й `variables` доступні як структуровані дані. При винятку історія доступна через `error.exchanges`. Внутрішні читачі runtime, токенів і тексту зберігають свої контракти; їхні запити входять в історію викликача.

`services/reports/HttpExchangeTrace.js` збирає історію централізовано через транспорт. Workflow використовує `withHttpWorkflow`; один користувацький запуск має спільний JSONL-журнал у `data/reports/http/`. Вкладені екшени мають власні ID, а фізичні запити записуються один раз. Перенаправлення, невдалі спроби й наявні повтори GET також враховуються. Журнал зберігає намір до HTTP-виклику й відповідь до розбору даних. Після аварії запис без відповіді означає невизначений результат; mutation автоматично не повторюється.

Спільна політика `httpHistoryPolicy.js` приховує credentials перед записом або поверненням історії. API/GraphQL-дані не обрізаються за довжиною, кількістю елементів чи глибиною. `body` містить структуровані дані, якщо їх вдалося розібрати; `rawBody` зберігає початковий текст запиту або відповіді після приховування секретів. Зберігаються також невалідний JSON, HTML-відмови API та JSON із помилковим JavaScript Content-Type. Якщо транспорт уже повернув об'єкт, зберігається цей об'єкт без вигаданого початкового тексту.

Виняток для великих службових сторінок задається явно через `historyPurpose` запиту: `session`, `access-token` або `runtime`. Це домашня сторінка, профіль, Accounts Center, Ads Manager і сторінки отримання runtime/маніфесту. Їхні неструктуровані відповіді замінюються розміром, назвами знайдених/відсутніх полів, результатом перевірки формату, ознаками наявності credentials, login/checkpoint, consent та підтвердження особи. Значення токенів і сам HTML таких сторінок не зберігаються. Призначення залишається тим самим під час перенаправлень; кожен перехід має окремий запис із URL, HTTP-статусом і Location. Content-Type `text/html` сам по собі не вимикає запис звичайної API-відповіді.

Статичні JS-ресурси (`historyPurpose: "static-resource"` або адреса ресурсу) зберігаються як опис. Байти фото та інших файлів не записуються: multipart містить усі текстові поля й метадані кожного файлу, включно з повторюваними назвами полів; двійкові тіла, image-відповіді та дані зображень у base64 приховуються.

`request.finished.operation` показує назву GraphQL-операції. `action.finished.result` зберігає діагностичні результати: лічильники постів, `postResults` зі статусами створення/датування та `failedStage`, `actionSteps` для About, код і текст відмови. Наприклад, `CREATE_CONFIRMATION` означає, що екшен не отримав `storyId`, а `BACKDATE` — що для створеного поста не підтверджено зміну дати. `action.failed` містить очищені дані винятку. Ці записи доповнюють HTTP-історію, не змінюючи правила повторів чи перевірки результату mutation. Старі журнали автоматично не доповнюються втраченими тілами відповідей.

`httpHistory` містить ID, шлях і кількість запитів; у разі проблем із диском також `storageWarning`. Збій журналювання не перетворює успішну mutation на невдалу. У стані профілю та задачі зберігається посилання замість копій великих відповідей. Фонова задача записує це посилання до завершення першого запиту, тому після перезапуску історія залишається доступною у звіті перерваної задачі.

`TaskReportManager` додає посилання до наявного JSON-звіту задачі. Деталі звіту в GUI та експорт Markdown включають історію з артефакту без загального обрізання логером. Дії фанок, які виконуються без фонової задачі, також отримують звіт через той самий менеджер. Markdown-звіт оформлення комент-акаунтів містить посилання профілів та секцію HTTP-історії. У деталях дії автозаливу є кнопка відкриття JSONL-файлу.

Для дій без фонової задачі звіт створюється зі статусом `running` до першого HTTP-запиту, а після завершення оновлюється під тим самим ID. Під час наступного запуску застосунку `TaskReportManager.recoverInterrupted()` позначає незавершені окремі звіти як `interrupted`; їхня вже записана HTTP-історія доступна для перевірки перед повтором.

Mock-перевірки історії: `node --test scripts/autoupload-history.test.js` (також входять у `npm run test:autoupload`). Формат нових екшенів закріплено у `facebook/autoupload/AGENTS.md`.

### Персональні HTTP-акаунти

У вкладці «Акаунти під коментарі» кнопка «Персональні автоаплоад» доступна без вибору профілю: номер можна ввести у вікні. Якщо вибрано кілька профілів, підставляється перший у списку. HTTP-вікно та звичайні персональні акаунти працюють незалежно й згортаються окремо; згортання зберігає стан і поточну чергу FP HUB. Значок під кнопкою запуску вручну відкриває AdsPower зі збереженням попередніх вкладок.

`PersonalAutouploadSessionManager` використовує `FacebookWebClient` і захищене `AutouploadSessionStore`. Сесія зберігається до читання активів і повторно використовується, доки залишається актуальною. Бізнес-інфо та перевірка способів оплати перевикористовують наявні API-екшени через явний `HttpAdsManagerContext`; телефон підтримує ручний код і наявну інтеграцію SMSPool. Огляд завантажує фанпейджі, РК і пікселі. Для Graph API використовується ID РК з префіксом `act_`.

В обох персональних вікнах API-профіль має назву за наступним внутрішнім номером (`P001`, `P002` тощо) та окремий вибір групи AdsPower. Зірочка зберігає групу за замовчуванням; початковий вибір шукає «FB Farm №2» / «FB Farm N2». Після створення застосовуються назва й група, а інтерфейс показує підтвердження. Номер остаточно визначається всередині атомарного створення акаунта, тому одночасні вікна не отримують однакову автоматичну назву. Помилка застосування назви або групи не запускає повторне створення API-клієнта.

FP HUB бере групи та профілі зі сховища автозаливів. Початкова обрана група — «FP Hubs», отримувач доступу — власник поточної персональної сесії. Доступ надається окремо або послідовно всім фанкам; між фанками діє затримка 10 секунд ±5 секунд, яку можна змінити. Зупинка завершує поточний запит і не надсилає наступні фанки. Невизначений результат припиняє чергу й позначає фанку для перевірки. Надіслане запрошення відображається як «Очікує».

Кожна HTTP-операція створює звіт у «Журналі» через `TaskReportManager`, а запити та відповіді зберігаються у спільному JSONL-форматі з прихованими credentials. Завершення або зміна персональної HTTP-сесії зупиняє пов’язану SMSPool-задачу. Прив’язка платіжної карти залишається окремим незавершеним етапом перевірки; успішне завантаження модулів або створення PTT не підтверджує прийняття карти Facebook.

Mock-перевірки: `node --test scripts/personal-autoupload.test.js` та `npm --prefix frontend run test -- src/test/personal-autoupload.test.jsx`. Ручна перевірка лише читання без SMS, створення активів і зміни Facebook: `electron scripts/manual/testPersonalAutouploadReadOnly.cjs 2559` через локальний Electron frontend-проєкту.

### Модулі шифрування платіжних карт

`FacebookBillingModules` для кожного додавання карти завантажує публічні фабрики JS через HTTP заново. Спільного кешу між операціями та файлового кешу немає; попередні файли `.cache/autoupload-billing/` не читаються. В межах однієї операції вже завантажений URL повторно не завантажується, паралельні звернення до нього об’єднуються.

Джерело URL — поточні зовнішні скрипти, карта ресурсів HTML та карти Bootloader у публічному JS. Зашиті резервні CDN-пакети видалено. Спочатку перевіряється іменний індекс модулів; за його відсутності пошук продовжується серед JS-ресурсів поточного manifest. Підготовка завершується лише за наявності всіх оголошених транзитивних залежностей з урахуванням адаптерів і bootstrap-конфігів. Ресурси читаються групами до чотирьох; після готовності графа пошук зупиняється. Inline-код приватної сторінки не виконується.

Підготовка робить до трьох викликів завантаження одного ресурсу з паузами; постійні HTTP 4xx, крім 408/429, не повторюються. Транспорт додатково може повторювати тимчасово невдалі GET. Частково виконаний JS не приймається як успішний ресурс. Якщо потрібних модулів немає, платіжний екшен до двох разів повторно читає HTML налаштувань оплати. При цьому фабрики та конфіги попередньої ревізії відкидаються, а ліміт спроб URL не скидається. Вичерпання спроб повертає `BILLING_MODULE_UNAVAILABLE` з назвою відсутньої залежності та діагностикою. Скасування припиняє повтори. Запит додавання карти цим механізмом не повторюється.

Mock-перевірки роботи без кешу, залежностей і оновлення ресурсів: `node --test scripts/billing-modules.test.js`.

`FacebookBillingModules.loadResources([{ url, moduleNames }])` перевіряє, що очікувані модулі визначає саме завантажений файл. Наявність однойменного модуля з іншого ресурсу не зараховується. Паралельно читаються до чотирьох файлів.

`loadResourceHints([{ url, moduleNames }])` використовує відому адресу як підказку для пошуку у поточному manifest: спочатку за назвою файлу, потім серед локалізованих пакетів тієї самої директорії. Директорія не підтверджує вміст: кожен кандидат перевіряється за фактичними визначеннями `__d`. Метод повертає `matchedUrl`, перевірених кандидатів та відсутні в них модулі. За відсутності відповідника стара адреса не завантажується автоматично.

За замовчуванням `loadRoots` використовує відповідності назв шести бандлів і модулів із `facebook/autoupload/encryption/billingModuleHints.js`, надані користувачем. Підказка може містити `fileName` замість URL; завантажується лише знайдений у поточному manifest ресурс. Підказки застосовуються також до нових транзитивних залежностей і після оновлення manifest. Це не підтвердження вмісту HAR: кожне визначення перевіряється після фактичного отримання JS.

Опція `resourceHints` у `loadRoots`, HTTP-екшені `addCreditCard` та `PersonalAutouploadSessionManager.execute("payment.add", input)` дозволяє явно замінити підказки; порожній масив вимикає їх. Вбудованого списку резервних CDN-адрес немає. `scripts/manual/billingResourceHints.json` містить лише явно надані користувачем адреси для ручної діагностики; звичайне додавання карти цей файл автоматично не читає.

Опція `resources: [{ url, moduleNames }]` у HTTP-екшені та персональному сервісі дозволяє явно завантажити відомі ресурси перед пошуком залежностей. Перевіряються визначення саме цих файлів; дані карти до них не надсилаються. Ручний сценарій приймає `--explicit-resources=scripts/manual/billingPaymentResources.json`. Запуск без `--modules-only` / `--browser-modules` виконує реальну спробу додавання карти, тому застосовується лише за прямою вказівкою користувача.

### Результати прив'язки карти через HTTP

Звичайний екшен за замовчуванням отримує два перевірені ресурси з `facebook/autoupload/encryption/billingPaymentResources.js`. GUI та workflow не потребують ручних CLI-прапорців. Це явний набір ресурсів перевіреного шляху; кожен файл завантажується через HTTP та перевіряється за визначеннями модулів. Після оновлення manifest ці ресурси завантажуються повторно. Недоступність або зміна пакета завершує підготовку помилкою до запису карти.

Екшен `addCreditCard` експортує `addCreditCardStatuses`. Відомі результати повертаються як `{ success, status, data, ... }`; інші GraphQL-, мережеві й runtime-помилки зберігають винятки. `success: false` не означає, що карту гарантовано не збережено: перевіряйте `data.cardSaved` та `data.paymentMethodId`.

| status | Значення |
| --- | --- |
| `CARD_ACCOUNT_LIMIT_REACHED` | Код Meta `4992003`: ця карта вже прив'язана до максимальної кількості рекламних акаунтів. `success: false`, `data.cardSaved: false`, `retryable: false`. Це ліміт акаунтів для карти, а не кількість карт на поточному акаунті. |
| `ADDED` | Отримано credential, `card_verification_status === SUCCESS`, а окреме risk-читання повернуло явну відсутність вимоги перевірки. |
| `AUTHENTICATION_REQUIRED` | Credential уже збережено; потрібне підтвердження. ID карти залишається в результаті. |
| `REQUIRES_RISK_VERIFICATION` | Credential збережено; risk-читання вимагає додаткової перевірки. |
| `RISK_CHECK_FAILED` | Credential збережено, але risk-читання не вдалося або відповідь неповна. Не повторюйте додавання. |
| `CARD_SAVE_REJECTED` | Credential повернуто, але статус перевірки відрізняється від SUCCESS та AUTHENTICATION_REQUIRED. Оригінальний статус збережено в `data.verificationStatus`. |

Приклад обробки в наступному workflow:

```js
const result = await manager.execute("payment.add", { sessionId, adAccountId, cardId });
if (result.status === "CARD_ACCOUNT_LIMIT_REACHED") {
    // Обробляємо ліміт прив'язок цієї карти окремою гілкою сценарію.
}
```

Персональний сервіс повертає весь компактний результат, також дублюючи поля `data` на верхньому рівні для сумісності наявного UI. `exchanges` у стан сервісу не копіюються. Відмова з окремим статусом потрапляє до звіту як `completed_with_warnings`; статус і код Meta зберігаються. Frontend-адаптер перетворює `success: false` на відмову GUI з `error.code === status`, щоб не показувати повідомлення про успішне додавання.

Екшен використовує той самий `HttpAdsManagerContext`, що й персональна сесія. Timeout, невалідна відповідь або відсутність credential після mutation блокують наступні записи в цьому контексті до перевірки результату. Відомий ліміт `4992003` не блокує інші дії та не повторює mutation. Окреме risk-читання після підтвердженого збереження також не запускає повторне додавання.

Mock-перевірки платіжних результатів: `scripts/billing-card.test.js`; передавання результатів через workflow та GUI перевіряють `scripts/personal-autoupload.test.js` і `frontend/src/test/personal-autoupload.test.jsx`.

## HTTP-коментарі: перевірений екшен

`facebook/autoupload/actions/comments/createComment.js` приймає готові `fbData`,
`{ feedbackId, text }` та `{ signal, beforeSend }`. Він не розбирає URL, не відкриває
браузер чи Ads Manager і не виконує додаткових GET або перемикання actor.
Використовує наявний GraphQL-транспорт та його локальну валідацію сесії.
`services/autoupload/resolveCommentTarget.js` окремо перетворює прямий HTTPS permalink
зі `story_fbid` на `storyId` та `feedbackId`; helper викликає зовнішній workflow.

Успіх підтверджує ID у `data.comment_create.feedback_comment_edge.node`.
Повертаються `commentId`, `legacyCommentId`, `commentFeedbackId`, `commentUrl`,
`postFeedbackId`, текст, час та HTTP-діагностика. Відсутні необов'язкові поля — `null`.
`tracedAction` додає `actionId` та `exchanges`; зовнішній `withHttpWorkflow` зберігає
HTTP-історію. Mutation не повторюється автоматично.

`scripts/manual/testHttpComment.js --execute-profile-2238` — одноразовий живий тест
узгодженого профілю та поста. Отримує звичайну Facebook-сесію через
`checkProfileSession` і зберігає результат у `data/reports/http-comment-2238-live.json`.
Наявність цього звіту блокує повторний запуск. Живий тест підтвердив створення
коментаря через два запити: GET сесії та POST GraphQL.

У вкладці «Автозаливи» виберіть акаунти → «Дії» → «Написати коментарі».
Модальне вікно приймає прямий permalink та список: один непорожній рядок — один
коментар. Черга попередньо показує тексти та порядок акаунтів. Дублікати рядків
зберігаються. Кожен акаунт має максимум одну спробу. Підтверджена відмова залишає
коментар наступному акаунту; невідомий результат пропускає коментар без повторної
публікації; успіх просуває чергу лише після отримання ID. Після вичерпання коментарів
решта акаунтів не використовуються. Залишок коментарів та всі спроби повертаються у
результаті фонової задачі. Скасування завершує чергу зі збереженням наявних результатів.

IPC `autoupload:comments` ставить задачу в наявну чергу та резервує вибрані профілі.
`AutouploadService.publishComments(ids, { postUrl, comments }, context)` отримує
свіжу соціальну сесію через `checkProfileSession` для кожного акаунта: без Ads Manager,
перемикання actor або окремого запиту його перевірки. Наявна локальна перевірка
належності сесії в HTTP-клієнті залишається. Повні запити та відповіді зберігаються у
спільному HTTP-журналі, компактні результати з ID — у задачі та історії профілю.

Після успіху сервіс `services/profile/actionCounters.js` додає або оновлює керований
блок у назві AdsPower: `Ім’я [AU_COMMENT=1]`. Інші ключі, наприклад `AU_REPLY`,
зберігаються; старий запис `AU_COMMENT=1` без дужок також підтримується. Дані
лічильників і підтверджені ID дій зберігаються у `AutouploadStore.actionCounters`.
Той самий ID зараховується один раз. Збій перейменування залишає локальне збільшення
для наступної синхронізації та показує попередження, не змінюючи успішний результат
коментаря. Перевищення ліміту 100 символів не обрізає ім’я. Збій збереження результату
коментаря зупиняє чергу; mutation не повторюється.
