# AdsBot Desktop GUI

У картці фанпейджа кнопка `Пересетапити` відкриває незворотне підтвердження,
дозволяє вибрати папку через системний Electron directory picker і ставить
`page-rebuild` у фонову чергу. Запуск доступний лише після checkbox-підтвердження;
якщо Meta не повернула дату створення Page, modal додатково вимагає дату вручну.

## Єдиний workspace (актуальний контракт)

Верхня навігація складається з вкладок «API-клієнти», «РК», «Фанпейджі» та «Журнал». Колишні окремі вкладки публікації й коментування вилучені. Після вибору активного API-клієнта IPC `workspace:client-load` паралельно повертає повні списки РК і фанпейдж; renderer кешує їх окремо за `accountKey`. Кампанії не прогріваються у фоні й завантажуються лише після відкриття РК.

Вкладка РК має внутрішні вкладки «Рекламні акаунти» та «Шаблони». Схема campaign template v5 більше не містить Pixel або UTM. Runtime Pixel і UTM беруться з глобальних `defaultPixelId`/`defaultUtm` у `data/app-state.json` або перевизначаються у формі конкретного запуску.

Глобальні обрані фанпейджі, GEO та маркер креативу зберігаються за Page ID у `data/page-preferences.json`. Вони не залежать від API-клієнта. Відкриття фанпейджі читає рівно 10 найновіших `published_posts`, після чого показує лише пости з HTTP(S)-посиланням у тексті; старіші сторінки Graph не запитуються.

Кнопка «Запустити новий креатив» створює запис у `data/creative-launch-jobs.json`. Parent workflow готує креатив, за бажанням видаляє URL-пости серед 10 найновіших, публікує й перевіряє новий пост, а далі одночасно запускає внутрішні гілки створення кампанії та паралельного коментування. Це внутрішня паралельність однієї задачі: усі верхньорівневі background tasks виконуються суворо по одній у глобальній FIFO-черзі.

`commentWorkerConcurrency` (1–5, стандартно 5) визначає кількість браузерів усередині одного паралельного comment workflow. Старий параметр паралельності кількох comment jobs більше не використовується GUI.

GUI працює як локальна Electron-програма. React renderer знаходиться повністю в
`frontend/`, а Facebook, AdsPower, Grok і файли залишаються у Node backend.
Renderer не отримує access tokens, cookies, proxy credentials або довільний
доступ до файлової системи.

## Запуск

Один раз встановіть frontend-залежності:

```powershell
cd frontend
npm install
cd ..
```

Потім запускайте програму з кореня проєкту:

```powershell
npm run gui:dev
```

Production-збірка renderer без Windows installer:

```powershell
npm run gui:build
```

Перед запуском мають бути заповнені кореневий `.env`, локальні
`data/facebookApi/accounts.json` і `data/facebookApi/proxies.json`. AdsPower
Local API має бути доступний для оновлення груп і запуску коментарів.

## Вибір Facebook-акаунта

Ліва панель викликає `AdsBotGuiService.getAccounts()` і показує:

- зелений статус — `/me` успішний;
- червоний — Meta підтвердила invalid token;
- жовтий — proxy, network або інша API-помилка.

Ключ вибраного акаунта й заповнені поля форм зберігаються локально у
`data/app-state.json`. Під час нового запуску Facebook-клієнти створюються
заново, а списки фанпейджів і рекламних акаунтів повторно запитуються після
вибору відповідної вкладки. Кожний запит фанпейджів,
публікації або рекламних акаунтів явно отримує `accountKey`. Неактивний профіль
можна переглянути в sidebar, але його Graph API-дії заблоковані.

## Керування Facebook API-клієнтами

У sidebar Facebook API-клієнтів кнопка `+` відкриває форму з `accountKey`,
`userAgent`, `accessToken` і cookies. `accountKey` унікальний. Олівець відкриває
часткове редагування: порожні секретні поля не змінюють збережені значення, а
поточні token/cookie ніколи не повертаються в renderer. Хрестик переміщує запис
в архів, а не видаляє його; архівний запис можна відновити відповідною кнопкою.
Форма cookies приймає також повний JSON-масив AdsPower.

## Шаблони кампаній

Вкладка «Шаблони» показує локальний список заготовок рекламних кампаній.
Шаблони зберігаються у `data/campaign-templates.json`, не прив'язані до
Facebook-акаунтів і мають автоматичний незмінний числовий ID. Підтримуються
створення, редагування, дублювання та видалення. Однакові назви дозволені.
Контракт шаблону v4 містить Pixel ID, країни, стать, точний вік `18–65+`, ручні Facebook
та Instagram placements, пристрої й мобільну ОС, довільний рядок UTM і режим розподілу бюджету між ad
sets. Також він містить справжню назву DSA-бенефіціара, прапорець однакового
платника та окрему назву платника. Випадкові юридичні назви не генеруються.
Старі записи автоматично отримують порожні DSA-поля, `any`, `18–65+`, усі пристрої й ОС, Facebook
Feed та вимкнені creative enhancements; перед запуском потрібно додати країну й Pixel.

## Робоча панель рекламних акаунтів

Після успішної публікації вкладка «Публікація» зберігає останні `pageId` і
canonical `postId` у стані програми та показує Post ID у read-only полі. У
майстрі кампанії біля фанпейджі й поста є окремі кнопки «Взяти з публікації».
Підставляти значення можна й через інший Facebook API-клієнт; його доступ до
фанпейджі та поста остаточно перевіряє preflight. Без успішної публікації
значення не підставляються.

Після вибору активного Facebook API-клієнта вкладка «Рекламні акаунти» одразу
отримує всі доступні РК. Ліва панель розділена на «Обрані РК» та «Інші РК».
Обрані можна впорядковувати перетягуванням, а інші автоматично показуються у
порядку: активні, потім неактивні.

Локальні назви й порядок зберігаються у
`data/ad-account-preferences.json`. Назва прив'язана глобально до Graph ID РК,
а склад і порядок обраних зберігається окремо для кожного `accountKey`.
Нові Graph ID автоматично отримують наскрізні назви `Ім’я 1`, `Ім’я 2` тощо.

Кампанії завантажуються при першому відкритті РК і кешуються на час GUI-сесії.
До двох обраних РК одночасно можуть прогріватися у фоні. Доступні Meta date
presets: сьогодні, учора, останні 7/30 днів і весь час. Таблиця показує тільки
ACTIVE та PAUSED кампанії, агрегований `lead`, spend і розрахований CPL.

У деталях активного РК кнопка «Створити кампанію» відкриває майстер website
lead-кампанії. Він приймає назву, шаблон, фанпейджу, Post ID, кількість ad sets,
бюджет одного ad set і start time в timezone РК. Preflight і створення показують
поетапний прогрес. Для аудиторій ЄС/ЄЕЗ preflight показує resolved DSA-бенефіціара
й платника та джерело кожного значення: шаблон або Meta default РК. За відсутності
обов'язкових значень запуск блокується. Часткові результати зберігаються у локальному журналі
`data/campaign-creation-jobs.json`; доступні безпечний повтор та підтверджене
видалення PAUSED-чернетки.

Форма майстра доступна одразу, поки шаблони та актуальні фанпейджі оновлюються
незалежно у фоні. Фанпейджі шукаються за назвою або ID. Після вибору сторінки
майстер показує рівно 10 найновіших опублікованих постів, найновіший зверху.
Пошук у списку працює за текстом та ID. Вибраний пост має компактне прев’ю з
картинкою, текстом, датою та canonical ID. Ручне розпізнавання Facebook-посилань
не використовується. Окремі кнопки оновлюють фанпейджі та пости, не запускаючи
жодних write-операцій у Meta.

## Масштаб інтерфейсу

Кнопка-шестерня у верхній панелі відкриває налаштування масштабу. Нове
стандартне значення — 130%, доступний діапазон — від 80% до 150% із кроком 10%.
Electron застосовує масштаб до всього вікна, а вибране значення зберігається у
`data/app-state.json` разом з іншим станом GUI.
Там само є параметр «Залишати campaign на паузі», який за замовчуванням
увімкнений і зберігається у стані програми.

## Публікація

Вкладка отримує безпечний список фанпейджів, готує креатив через
`CreativeManager`, підставляє обов'язковий offer URL і викликає наявний workflow
публікації. Картинка необов'язкова; підтримуються JPG, JPEG, PNG і WEBP.

Після успіху GUI показує post ID і Facebook permalink. Geo, назва креативу,
offer URL і permalink автоматично переносяться у форму коментарів. Також GUI
шукає першу групу, назва якої містить точний geo-маркер на кшталт `[HU]`, і
додає її до вибору без видалення вже вибраних груп.

## Коментарі та групи AdsPower

Коментарі пишуть профілі вибраних груп AdsPower, а не вибраний Graph
API-акаунт. Offer URL тут необов'язковий: порожнє значення замінює точні
`<LINK>` у коментарях порожнім рядком.

Кнопка оновлення груп використовує лише Profile API V2. `AdsPower.getProfiles()`
отримує профілі сторінками по 100, після чого `AdsPowerGroupService` збирає
унікальні групи й атомарно оновлює `data/adspower-groups.json`.

Коментування запускається як фонова задача. До двох задач із різними групами
можуть працювати паралельно; ліміт `1–5` задається в налаштуваннях. Якщо задачі
мають хоча б одну спільну AdsPower-групу, пізніша чекає звільнення групи. Всі
сценарії використовують один екземпляр `AdsPower`, тому його внутрішня черга й
пауза між API-запитами залишаються спільними.

## Фонові задачі

Глобальна права панель показує comment і campaign jobs незалежно від активної
вкладки. Панель згортається у вузьку смугу, а на невеликій ширині відкривається
поверх workspace. Картка містить статус, причину очікування, прогрес, проміжні
лічильники та помилку. Активну задачу можна зупинити на безпечному етапі;
завершені записи зберігаються до ручного очищення.

Задачі зберігаються в `data/background-tasks.json`. Після перезапуску старі
`queued` і `running` переходять у `interrupted` і автоматично не повторюються.
Campaign create, retry та cleanup використовують одну глобальну write-чергу.
Спроби кампаній додатково зберігають відомі Graph ID у
`data/campaign-creation-jobs.json`.

Під час закриття програми з незавершеними задачами показується підтвердження.
Після підтвердження черга скасовується, а активні сценарії зупиняються після
поточного зовнішнього запиту та cleanup відкритого AdsPower-профілю.

## IPC і безпека

Electron працює з `contextIsolation: true`, `nodeIntegration: false` та sandbox.
Preload відкриває тільки конкретні методи `window.adsBot`. Generic IPC не
експонується. Backend-помилки серіалізуються без stack і конфігів запиту.
Зовнішньо дозволено відкривати лише HTTPS-посилання домену Facebook.

`comments:run` і `campaigns:create-start` одразу повертають `taskId`, не чекаючи
завершення. Історія й керування доступні через `tasks:list`, `tasks:cancel`,
`tasks:dismiss`, `tasks:clear-finished`; зміни надходять подією `tasks:updated`.

`post:publish` також одразу ставить публікацію у глобальну послідовну чергу.
Форма після enqueue не блокується, а останній Post ID оновлюється після події
успішного завершення задачі.

Вкладка «Журнал» читає структуровані події з `data/logs` через пагінований IPC
і показує незалежні звіти задач із `data/reports/tasks`. Технічні деталі logger,
redaction та retention описані в [logging.md](logging.md).

У налаштуваннях коментування можна вибрати звичайний або `Headless` запуск
AdsPower та окремо вимкнути завантаження зображень. Параметри копіюються в
задачу під час `comments:run`, тому подальша зміна налаштувань не впливає на
вже поставлені задачі. Backend передає AdsPower Open Browser V2 поля
`headless: "0" | "1"` та, за потреби,
`launch_args: ["--blink-settings=imagesEnabled=false"]`. Інші ресурси, зокрема
відео та шрифти, цим прапорцем не блокуються.

## Перевірка

```powershell
npm run test:campaign
npm run test:all
npm run gui:build
```

`test:campaign` є типовою швидкою перевіркою форми, IPC, черги, журналу та
Graph API payload-ів запуску РК. `test:all` додатково запускає всі безпечні
backend mocks і повний frontend-набір. Runner показує час кожного файла та
загальну тривалість.

Mock-тести не створюють реальних Facebook-постів, не запускають браузерні
профілі AdsPower і не виконують платних Grok-запитів.
